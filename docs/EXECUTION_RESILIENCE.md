# 执行效率、查询恢复与持续异常可见性

本文记录执行保护与后续通用性能优化。当前唯一开发入口为 `main`，版本与最新验证见 [HANDOFF](../HANDOFF.md)／[VALIDATION](VALIDATION.md)；末尾 2026-10-21 的部署数字是历史记录。TEST／LIVE 后台互斥及十账户局部错误边界见 [通用优化](archive/TEST_OPTIMIZATION_20261029.md)。

下述改进保留最高买价、预算、标的筛选、事件内仲裁、止盈止损、所有权、原账本和缺报价按成本暂计规则。没有引入故障后的自动恢复 RUNNING；用户暂停与现有故障暂停行为不变。

## 未提交的过时买单

LIVE 会在签名后、账户核对后，以及账本门禁／SDK 队列等待结束后的真正提交边界，检查当前有效本地卖盘是否仍有能在已签买价内成交的深度。

若该价格内已没有可执行卖盘，且当前进程能证明未跨过任何可能 POST 边界，终结这份未发送意图，由现有策略重新判断。新的价格必须重新满足完整策略、原最高买价、含费预算、最小份额及市场资格；不直接修改已签金额，不增加预算。更低价格和仍有可执行部分深度的 FAK 保持原签名，避免不必要的重签。未提交旧单终态投影完成后，可在同一代次、启动状态、参数及完整 readiness 不变时合并执行一次原策略重评；每个 Event 每 5 秒最多一次即时重评，冷却记录最多 512 项，其余回到普通控制轮，避免价格抖动形成连续签名循环。关闭时取消并等待这些任务。

已经可能发出、超时或结果未知的订单保留原确定性身份、额度和 Event 锁，先查询原单；不得借重新估价创建另一份订单。价格变动仍可能发生在本地检查之后，因此无法消除全部零成交。

## 逐笔核对结果

并发查询多个自有订单后，对每份可验证结果独立应用终态、已确认成交及对应额度变化。某一笔请求超时或返回不可信数据，不再阻止其他已完整核实的订单更新。

失败那笔保留自有额度和锁；任何整体核对失败仍关闭 LIVE readiness 与开放挂单门禁，禁止新增 BUY。只有完整成交证据覆盖、数量边界及身份检查通过才能终结，不能把查询失败、缺少交易或未知状态解释为零成交。

## 公开发现分页的有限重试

仅对公开 Event 发现分页的超时及 HTTP 429／502／503／504 重试同一页，最多三次请求，单页总请求与等待期限 60 秒。等待采用有界退避与抖动，Retry-After 数值或日期最多采用 5 秒。

鉴权错误、其他 HTTP 状态、格式或身份错误不自动重试；私有下单、取消和资金接口不使用此机制。完整分页成功后提交发现结果，失败保留旧元数据。扫描间隔从上一轮结束起计算，代码默认 300 秒，Compose 默认通过 `PM_DISCOVERY_SECONDS` 配置为 900 秒。

## 已识别赎回的独立推进

一个有界单消费者在公开结算查询等待期间推进已有 claim，新识别的 claim 也可及时排入该队列。每个 claim 每轮最多推进一次；账户级 nonce 所有权、签名前检查、原交易字节复用、取消后签名结果接管、链上确认和真实账户现金核对保持。

公开市场请求慢不会先挡住全部已有 claim，但 RPC 本身慢、账户已有未决交易或核对未通过仍可能推迟赎回。没有并发抢用钱包 nonce，没有把应收直接变成可用现金。

## 扫描与结算查询可见性

`/api/health` 增加 `serviceFreshness`，将公开发现与每个模式的自有结算查询分开报告。只公开成功／尝试时间、允许的错误代码、失败次数及汇总数量；不公开持仓市场、Token、钱包、数量、金额或 RPC 地址。认证页面提供相同当前状态及关注提示。

一次短暂故障处于 `retrying`。连续至少三次实际查询失败且持续至少 60 秒，或失败持续达到 15 分钟时为 `attention`。首次扫描、LIVE 扫描和结算查询的有效覆盖期限为 15 分钟。TEST 共享目录首次扫描成功后，期限取「配置的扫描间隔加 5 分钟」与 15 分钟中的较大值，为正常分页留出时间。默认部署下为 20 分钟，页面按实际期限显示提示。期限始终从上次成功计算，开始新一轮或反复重试均不会延后期限。

这些期限仅用于诊断。目录扫描周期和交易调度沿用配置。公开健康接口的非致命关注状态使用 HTTP 200，实际账本、存储或后台任务错误仍按各自健康检查报告。

结算观察按自有市场保留失败状态，一个健康市场的成功不能掩盖另一个持续失败的市场；恢复或不再需要查询后清除当前异常。新增加的持仓有自己的首次查询宽限，不继承进程运行了数日的旧启动时间。

提示不暂停正常持仓、不隐藏资金或有报价持仓、不启动／解锁 LIVE、不重启服务。观察状态在内存中重新建立，原持久化旧异常不能当作当前失败。

## 无订阅行情连接的关闭

共享行情源会先取消所有已无订阅的连接，再并发等待关闭完成。关闭连接本身已退订，无需在关闭前再逐个发送退订请求。这样避免大量连接的关闭握手串行累加，仍会等待清理完成后才继续；不会提前释放账本或进程锁。

仍有订阅的连接保留原任务和完整盘口，只按原规则增减订阅。本项同时适用于共享行情源与 TEST 行情源，不改市场筛选、扫描周期、成交或交易决策。回归覆盖 64 组并发关闭、关闭异常、调用者取消，以及保留连接继续接收完整盘口。

## 无变化的市场分组复用

TEST 与 LIVE 每轮仍按原频率重新判断全部候选市场的资格及周期归属。只有合格 Token 的迭代顺序、对应周期 ID 顺序以及已保存分组对象都未变化时，才复用已构建的市场分组；任一项变化就按原顺序重新构建。无持仓、无活动订单的刷新状态复用同一个不可变空值，减少大市场范围下反复创建临时对象。

参数、元数据、时间门槛、结算、市场可用性、持仓及订单状态的检查都保留。控制状态、待处理事件、终态重试和时间敏感事件继续按原规则更新；异常时丢弃复用依据，下次重新计算。本项不改变订阅范围、扫描或评估频率，不关闭垃圾回收，不降低 SQLite 落盘强度。回归以已部署旧实现为基准，对比普通 Runtime、TEST Runtime 和受控 LIVE 的分组/成员顺序及控制状态，并逐步比较实际模拟买卖轨迹。

清理不再监控的执行品种时，仅收集既未监控、又没有交易历史的映射，避免每轮先复制全部活跃品种。仍按原字典顺序调用同步的原生缓存清理，成功后删除对应映射；异常时保留原来的已完成部分和停止位置。盘口清理、历史执行身份保护及之后的冷元数据清理保持原样。新旧函数对照覆盖真实模拟买卖历史、原生品种保留及中途异常；大批活跃品种无需清理时另核对分配量。

## 公共行情与页面的重复工作

公开发现仍完整读取、规范化并核查每一页。只有新旧 Token 的全部字段相等时，分页积累和最终发布才复用已有不可变对象，避免下一轮扫描再保留一份相同的元数据图。任何字段变化仍走原更新路径；完整分页成功后才发布，失败和取消保留旧结果。发布前继续处理扫描期间收到的 WebSocket tick 变化，旧分页不能覆盖更新的 tick。账户资金、模拟盘口消耗和订单状态不参与共享，也不增加市场或历史裁剪。

普通公共 WebSocket 行情帧使用既有 `msgspec` 依赖进行严格形状解码：最多四层容器，标量为字符串、整数、布尔值或空值。行情中以字符串提供的价格和数量继续交给原来的数值转换。含 JSON 浮点数、更深结构、扩展值或不兼容编码的帧回退到原 `json.loads`，保留原浮点舍入、递归限制及错误行为。始终先完整解析一帧，再按原顺序处理各条消息并逐条让出事件循环；PING/PONG、订阅更新、取消和消息处理逻辑不变。

离线普通帧基准中，约 0.747 MB 的解析中位数由 2.128 ms 降为 1.265 ms，约 14.427 MB 的帧由 44.031 ms 降为 30.295 ms；解码后对象图的峰值基本不降。回退不是加速保证：末字段为浮点数的样例因多一次尝试，中位数由 2.135 ms 增为 3.590 ms。因此本项仅有普通帧解析效率证据，不能解释全部长尾；现场停在解析函数的取栈仍可能包含垃圾回收、缺页和调度等待。

公共行情连接在同一个服务生命周期中复用一个默认 TLS 上下文，避免每个分组和每次重连重复加载证书库。证书链、主机名校验和默认信任源均保留；创建失败仍按原连接恢复路径处理。信任配置在该服务首次连接时读取，更新系统信任配置后须重建服务才能采用。该复用只用于公共行情 WebSocket，不修改 LIVE 私有客户端、钱包、签名、下单或赎回。

网页对 `/api/dashboard` 显式传入 `compact_diagnostics=true`。此时仅省略页面从未使用的全量 `marketScan.diagnostics.pendingEvents`，并只为当前可见候选构造缺盘口详情。全量候选计数、排序、分页、可见行的每个字段、持仓与资金、连接状态及错误详情均保留；刷新频率和账户选择不变。未传参数或传 `false` 时，API 沿用完整诊断响应，现有外部工具无需改动。冷账户仍沿用原只读路径。

本地合成基准使用 12,719 个 Token、6,360 个事件、6 万个保留对象，开启普通垃圾回收并连续读取 20 轮；为单独测候选构造，未加入连接诊断载荷。行情恢复、页面显示 20 行时，响应从约 643 KB 降到 46 KB，构造中位数从 8.13 ms 降到 4.85 ms，序列化从 16.61 ms 降到 0.89 ms。默认响应与改动前函数对照，在就绪／恢复状态及多个分页大小下，除时间戳外 JSON 字节一致；精简响应仅少上述未使用字段。这是本地分配与载荷证据，不是服务器延迟保证。

## 验证与发布边界

专项受控测试覆盖：签名及最后提交边界的价格变化、较好价格及部分成交、超价和预算限制、可能已 POST 的未知结果、混合成功／失败的订单核对、分页恢复及耗尽、关闭取消及迟到响应、慢查询期间已有／新识别结算、每轮唯一推进、持仓逐项失败恢复、首次宽限、诊断隐私及页面陈旧数据保护。

发布前运行完整 Python／页面回归和 Ruff，并核对 GitHub 双架构及镜像检查。服务器先构建、保全停机一致性备份，再核对十个 TEST 与 LIVE 账本的逻辑值、原生事件与权益历史、参数、代次、钱包、受保护配置及既有存储维护。上述优化不需要数据库 schema／codec 迁移、在线压缩或 VACUUM；实际版本及验收结果见 [当前交接](../HANDOFF.md)。

部署结果以最新 HANDOFF 记录为准。TEST、受控 LIVE 测试或 CI 通过不证明真实资金收益；地区、资金、POL 及真实买卖／赎回闭环仍需实际核验。

2026-11-13 在应用仍为 `c44c1da`、尚未重启或部署本轮新代码时，用户在另一窗口移除了另一个程序，只保留 PM 容器运行。随后正常扫描从 07:15:04 UTC 开始，07:18:36 UTC 成功检查 368,590 个市场，清除上次扫描错误。320.21 秒的 88 次健康查询中，中位数 143.25 ms、最大 11,968.57 ms；38 次处于行情恢复，持仓未就绪数最高 38。末次 07:19:42 UTC 查询耗时 298.48 ms，64/64 组、12,719 个盘口全部就绪，持仓未就绪数为 0；窗口内不可用持仓及后台错误均为 0。证据为服务器 `/var/log/pm-nautilus-isolated-c44c1da.log`。

另一程序仍运行时，同一应用曾在较早窗口出现约 56.7 秒健康请求和正常轮次扫描 `ReadTimeout`。资源释放后旧版扫描恢复成功、长尾仍存在，说明有必要区分宿主资源压力与代码重复工作。这不是当时尚未部署的新代码的效果；两个窗口的负载、行情和网络条件未严格匹配，不能承诺固定改善比例，也不能据此认定长尾已消除。

本地测试与分配基准同样不能单独证明线上长尾、扫描超时和连接恢复已解决。须将请求延迟、扫描阶段、实时取栈及换页／I/O 压力按时间对齐，不能将全部停顿归因于垃圾回收或网络。诊断期限、连接心跳、扫描范围和 SQLite 落盘强度不因本轮优化而调整；本轮代码改动未操作其他应用。完整观测窗口及最终验收以 HANDOFF 为准。
